# Hotdeal Agent

매일 하던 핫딜 탐색·평가·알림 확인을 대신하는 개인 Agentic workflow.
2025년 12월부터 직접 개발·운영 중. 사용자는 나 한 명이고, 7개월째 매일 쓰고 있다.

시작 계기: 새벽에 240만 원대 태블릿이 가격 오류로 83만 원에 풀린 적이 있다. 깨어 있었는데도 그 정보를 못 받았다. 다음부터는 놓치지 않으려고 만들었다.

## 워크플로 그래프

오케스트레이션 단위로 나눠서 그린다. LangGraph식 상태 그래프로 읽으면 되는데, 구현은 프레임워크 없이 Python + SQLite다 — 각 노드는 함수, 상태는 DB 테이블, 아래 분기·폴백은 전부 코드에 실존한다. 모든 판단의 사유는 `decision_log`(19,775건)에 남는다.

### 공통 레이어 — fetch 라우팅과 브라우저 안전 게이트

싼 도구(경량 HTTP)로 될 일은 싼 도구로, 안 되는 곳만 비싼 도구(실브라우저)로 보낸다.

```
fetch(url)
 ├─ backend 강제 지정?            ─► 해당 백엔드
 ├─ source_kind == browser_required? ─► [real browser]
 ├─ domain ∈ 브라우저 필수 목록?      ─► [real browser]
 └─ else                          ─► [경량 HTTP]

[real browser] 진입 전 de-risk 게이트
 └─ 무인 실행은 실적이 증명될 때만: 성공률 ≥0.95 AND 누적 실행 ≥20회
    (browser_run_log로 추적 — 자율성은 기본값이 아니라 실적으로 획득)
```

### ① Scan / Digest — 수집·평가·알림 (30분 주기 / 하루 5회)

```
crawl(소스별)
 ├─ 실패 ─► source_health 기록 ─► 연속 실패 ─► circuit breaker ─► quarantine
 └─ 성공 ─► parse ─► price_meta 추출
             ├─ 스키마·값 검증 실패 ─► 미편입 + 로그
             └─ 통과 ─► score ─► intelligence(anomaly·why_now·lifecycle)
                         ─► oracle price gate (가격 증거 검증)
                           ├─ urgent 판정(신호 가중합 ≥ 2.0) ─► 즉시 알림
                           ├─ digest 후보(anomaly ≥ 0.45 or why_now ≥ 0.70) ─► top-N 요약 발송
                           └─ 해당 없음 ─► 저장만 (사유는 decision_log)
```

### ② Feedback — 자연어 피드백 상태 기계 (상시 HTTP 서버)

```
자연어 답글/HTTP 수신 ─► raw 저장(status=queued)   ← 이후 뭐가 실패해도 원문은 이미 안전
 ├─ 초단문(이모지 수준) ─► 즉시 applied
 └─ 그 외 ─► 정규식 1차 분류 ─► LLM 구조화(status=llm_running)
              ├─ 성공 ─► validator ─► ratings·signals·preferences 반영(applied)
              └─ 실패 ─► status=llm_failed (원문 보존)
                          └─ recovery 잡 재시도 ─► 복구 시 applied
                             (실사례: llm_failed 8건 전량 복구, 현재 13/13 applied)
```

### ③ Rebuttal — 싫다고 하면, 근거가 강할 때 한 번은 반박

dislike를 그대로 학습하지 않는다. 증거가 강한 딜이면 에이전트가 한 번 되묻는다.

```
dislike 발생
 ├─ 싫은 이유가 이미 기록됨 ─► 종료 (선호에만 반영)
 └─ 이유 없음 ─► evidence_score (oracle confidence posture)
      ├─ 증거 약함 ─► 조용히 수용
      └─ 증거 강함(기준선 대비 실제 저가) ─► 하루 1건 제한 확인
           ─► 반박 카드 발송: 근거 제시 + 이유 칩 요청
              (💸비쌈 🥱노관심 📦이미있음 🔁너무자주 🤔품질의심 ✍️직접말함)
           ─► 응답이 dislike_reason으로 쌓여 선호 학습의 입력이 됨
```

### ④ Quest — "!찾아줘" 자연어 퀘스트 (능동 탐색 + 스트림 매칭 + 워치 핸드오프)

```
"!찾아줘 <상품> [목표가]" ─► 퀘스트 등록
 ├─ (a) 능동 탐색: 쇼핑 API + 내부 딜 이력 검색, 20시간 간격
 │       └─ validation oracle 통과분만 보고 (제목 유사도·기준선 신뢰도·가격 상식선)
 ├─ (b) 스트림 매칭: 이후 크롤되는 모든 신규 딜을 활성 퀘스트와 대조 ─► 일치 시 즉시 알림
 └─ (c) 핸드오프: 목표가 미달 ─► deal_watch(target_price)로 이관해 계속 감시
"!그만 <상품>" ─► 해제,  "!목록" ─► 활성 퀘스트 조회
```

### ⑤ Source Scout — 소스 발굴·승격 (매일)

```
scout task 큐 ─► LLM run으로 후보 소스 조사 ─► 후보 등록
 ─► shadow crawl(운영 미반영 수집, 120분 주기) ─► source score 산출
     ├─ 기준 미달 ─► warmup 유지 또는 quarantine
     └─ 기준 충족 ─► 승급 후보 알림 ─► [사람 승인] ─► 운영 편입(trusted)
발굴은 자동, 편입은 승인. 현재 분포: trusted 1 · warmup 11 · quarantined 6
```

### ⑥ Self-review — 일일 회고 (매일 23:30)

```
오늘의 알림·미알림 딜 복기
 ├─ missed: 좋은 딜인데 안 보냄
 └─ false-positive: 보냈는데 반응 나쁨
 ─► daily_reviews 적재 ─► 임계값·가중치 조정의 근거
```

## 핵심 설계 결정 5가지

### 1. "5,000원 할인"을 판매가로 오인하던 문제 → price meta schema
LLM/파서가 할인액·쿠폰 조건을 실판매가로 오인하는 오류가 있었다. 가격·할인·조건부 혜택을 분리한 스키마로 바꿔서 이 오류 유형 자체를 제거했고, 회귀 테스트로 고정했다 (운영 중 가격 메타 33,335건).

### 2. 자연어 피드백은 raw 보존 → 구조화 추출의 2단계 (fail-soft)
피드백 텍스트를 LLM으로 즉시 구조화하지 않는다. 원문을 먼저 저장하고, 구조화(평점·신호·가중치 추출)는 별도 단계로 분리했다. 실제로 LLM 추출이 실패한 피드백 8건이 있었지만 raw가 남아 있어서 이후 전량 복구·적용됐다 (현재 13/13 applied).

### 3. 신규 소스는 shadow → 점수 → 승인의 3단계 승격
새 크롤링 소스를 발굴해도 바로 운영에 넣지 않는다. shadow 모드로 수집만 하면서(현재 6,881건) 소스 점수를 확인하고, 승인을 거쳐야 운영 소스가 된다. 소스 자동 발굴(scout)에 LLM run을 쓰지만 자동 활성화는 막아놨다 — 발굴은 자동, 편입은 승인.

### 4. 낮은 리스크는 자동 차단, 높은 리스크에만 사람
스키마·값 오류는 validator와 테스트 204개가 자동으로 막는다. 실패하는 소스는 quarantine·circuit breaker가 자동 격리한다(현재 quarantined 6개). 사람 승인은 신규 소스 편입 같은 고위험 결정에만 둔다. 실브라우저 같은 비싼 도구의 무인 사용은 성공 실적(≥0.95, ≥20회)이 쌓여야 허용된다.

### 5. 선호 학습은 단순하고 관측 가능하게 (EMA)
이모지 평점(정량)과 자연어 피드백(정성)이 같은 선호 테이블에 합류한다. 평점을 [-1, +1]로 정규화해 feature key(카테고리·소스·가격대·브랜드 등)별 가중치를 EMA(α=0.15)로 갱신한다 — 최근 평가일수록 가중되고 오래된 선호는 서서히 잊힌다. 자연어 신호는 confidence로 감쇠해 반영한다. dislike는 그대로 먹지 않고, 증거가 강하면 Rebuttal이 한 번 이유를 되묻는다.

## 운영하면서 확인한 것 (한계 포함)

- 결정 로그(19,775건)가 있어서 "왜 이 딜이 안 왔지?"를 매번 로그로 재현해 답할 수 있었다.
- 명시 라벨(평점·자연어 피드백)은 생각보다 안 쌓인다. 수십 건 수준이라 선호 학습은 방향성 파악까지가 정직한 성능이고, 그래서 implicit 신호와 가격 기준선의 비중을 키웠다.
- 게이트가 실제로 작동하는지는 차단 실적으로 본다. 소스 상태 분포(trusted 1 vs quarantined 6)가 그 결과다.
- 단위 파싱은 조용히 틀린다. "512GB"의 G를 그램으로 읽어 노트북에 원/100g 단가가 계산된 적이 있다 — 정규식에 부정형 예외를 박고 회귀 테스트로 고정했다.

## 스택과 기여 경계

- **Python** (도구 계층·검증·테스트 전부), **SQLite** (27테이블 상태 버스), 스케줄러 기반 반복 실행, Discord 게이트웨이 런타임(Zig).
- LLM 호출은 자체 런타임의 run API를 경유한다 (특정 벤더 SDK 비종속).
- 기획·설계·운영·승인 결정은 내가 소유한다. 코드 작성에는 AI 코딩 에이전트를 적극 활용했고, 에이전트 산출물은 테스트·validator를 통과해야 반영된다.
