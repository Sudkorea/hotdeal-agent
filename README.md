# Hotdeal Agent

**매일 반복하던 핫딜 탐색·평가·알림 업무를 대신하는 개인 Agentic Workflow.**
2025년 12월부터 현재까지 직접 개발·운영 중이며, 사용자는 나 한 명이고, 7개월째 매일 쓰고 있다.

> 어느 새벽, 정가 240만 원대 태블릿이 가격 오류로 83만 원에 풀렸고 주문 취소도 되지 않았다.
> 나는 그 시간에 깨어 있었는데도 그 정보를 받지 못했다. 이 시스템은 그날의 분함에서 시작됐다.

| **알림 발송** | 3,750건 (urgent / digest 이원화) |

| **코드** | Python 도구 계층 43개 모듈 16,199줄 / 단위 테스트 31개 파일·204개 함수(4,976줄) |

완전 자율 챗봇이 아니다. **도구 실행(tool orchestration) + 상태(SQLite) + 검증·승인 게이트 + 로그**로 구성된, 사람이 감독하는 stateful workflow다.

## 시스템 구조

```
  핫딜 소스(다중) ─┐                        ┌─ Discord 봇 ── 사용자(나)
  가격 API ────────┤                        │   OUT: urgent/digest 알림, 소스 승급 제안, 일일 회고
                   ▼                        │   IN : 1~5 이모지 평점, 답글 자연어 피드백
        ┌─────────────────────┐             │
스케줄러 ─► job dispatcher     │◄────────────┘
(11 jobs)│  crawl → score      │
         │  intelligence       │        ┌──────────────────────────┐
         │  notifications      │◄──────►│ SQLite deals.db (27테이블) │
         │  shadow / scout     │  상태  │  = 공유 상태 버스           │
         │  ratings / review   │  버스  │  잡들은 서로 직접 호출하지    │
         └─────────┬───────────┘        │  않고 DB로 비동기 협력       │
                   │                    └──────────────────────────┘
         상시 HTTP 피드백 서버 ── 자연어 피드백 → raw 보존 → LLM 구조화 → validator → 선호 반영
```

**폐루프**: 크롤 → 점수 → 알림 → 사람 반응(이모지·자연어) → 선호 갱신 → 다음 점수.
내 판단이 학습 신호로 흡수되고, 다음 추천이 달라진다.

## 핵심 설계 결정 5가지

### 1. "5,000원 할인"을 판매가로 오인하던 문제 → price meta schema
LLM/파서가 할인액·쿠폰 조건을 실판매가로 오인하는 오류를 겪은 뒤, **가격·할인·조건부 혜택을 분리한 스키마**를 설계해 이 오류 유형 자체를 제거했다. 회귀 테스트로 고정 (운영 중 가격 메타 33,335건).

### 2. 자연어 피드백은 raw 보존 → 구조화 추출의 2단계 (fail-soft)
피드백 텍스트를 LLM으로 즉시 구조화하지 않는다. **원문을 먼저 저장하고**, 구조화(평점·신호·가중치 추출)는 별도 단계로 분리했다. 실제로 LLM 추출이 실패한 피드백 8건이 발생했지만 raw가 보존돼 있어 이후 **전량 복구·적용됐다** (현재 13/13 applied). 실패해도 데이터를 잃지 않는 구조가 이 시스템의 기본값이다.

### 3. 신규 소스는 shadow → 점수 → 승인의 3단계 승격
새 크롤링 소스를 발굴해도 즉시 운영에 편입하지 않는다. **shadow 모드로 수집만** 하면서(현재 6,881건) 소스 점수를 확인하고, 사람 승인을 통과해야 운영 소스가 된다. 소스 자동 발굴(scout)에 LLM run을 쓰지만, **자동 활성화는 금지** — 발굴은 자동, 편입은 승인.

### 4. 낮은 리스크는 자동 차단, 높은 리스크에만 사람
스키마·값 오류는 validator와 테스트 204개가 자동으로 막는다. 실패하는 소스는 quarantine·circuit breaker가 자동 격리한다(현재 quarantined 6개). 사람 승인은 신규 소스 편입 같은 **고위험 결정에만** 배치했다 — 검수 지점을 좁히는 설계.

### 5. 선호 학습은 단순하고 관측 가능하게 (EMA)
이모지 평점(정량)과 자연어 피드백(정성)이 같은 선호 테이블에 합류한다. 평점을 [-1, +1]로 정규화해 feature key(카테고리·소스·가격대·브랜드 등)별 가중치를 **EMA(α=0.15)로 갱신** — 최근 취향일수록 가중되고 오래된 선호는 서서히 잊힌다. 자연어 신호는 confidence로 감쇠해 반영한다.

## 운영에서 배운 것 (정직한 한계 포함)

- **로그가 없으면 운영이 아니다.** 이벤트·결정·소스 헬스 로그(결정 로그 19,775건) 덕에 "왜 이 딜이 안 왔지?"를 매번 재현해서 답할 수 있었다.
- **명시 라벨은 생각보다 안 쌓인다.** 이모지 평점·자연어 피드백은 수십 건 수준 — 선호 학습은 "방향성 파악"까지가 정직한 성능이다. 그래서 implicit 신호와 기준선(가격 스냅샷) 비중을 키웠다.
- **게이트는 존재가 아니라 차단 실적으로 증명된다.** 소스 상태 분포(trusted 1 vs quarantined 6)가 게이트가 장식이 아니라는 실측 증거다.

## 스택과 기여 경계

- **Python** (도구 계층·검증·테스트 전부), **SQLite** (27테이블 상태 버스), 스케줄러 기반 반복 실행, Discord 게이트웨이 런타임(Zig).
- LLM 호출은 자체 런타임의 run API를 경유한다 (특정 벤더 SDK 비종속).
- 기획·설계·운영·승인 결정은 전부 내가 소유한다. 코드 작성에는 AI 코딩 에이전트를 적극 활용했고, 에이전트 산출물은 테스트·validator를 통과해야 반영된다 — 이 프로젝트 자체가 "AI와 빠르게 만들되, 검증 가능한 형태로만 수용한다"는 작업 방식의 실물이다.
