# 수집부터 피드백 반영까지

[제품 소개](../README.md) · [운영 사례와 수치](OPERATIONS.md)

2026-07-13 기록에 설명된 동작입니다. 코드 실행 안내가 아니라, 각 단계의 입력·판단·다음 동작을 정리한 문서입니다.

## 1. 수집 도구 선택

기본은 경량 HTTP 요청입니다. 백엔드를 명시하면 해당 도구를 사용하고, 소스 분류가 `browser_required`이거나 도메인이 브라우저 필수 목록에 있으면 실제 브라우저로 보냅니다.

무인 브라우저 실행 조건은 `browser_run_log`의 **성공률 0.95 이상, 누적 실행 20회 이상**으로 기록돼 있습니다. 브라우저 사용 기준이지 상품 정보의 정확도 지표는 아닙니다.

## 2. 수집·평가·알림 — Scan / Digest

수집은 30분 주기, 정기 요약은 하루 5회입니다.

```text
소스별 수집
    ├─ 실패 → source_health 기록 → 연속 실패 시 차단·격리
    └─ 성공 → 파싱 → 가격·할인 조건 추출
                        ├─ 스키마·값 오류 → 미편입·사유 기록
                        └─ 통과 → 점수·상황 신호 평가 → 가격 근거 검사
                                                     ├─ 즉시 알림
                                                     ├─ 정기 요약 후보
                                                     └─ 저장만
```

평가에는 `anomaly`, `why_now`, `lifecycle` 신호를 사용합니다. 가격 근거 검사 단계의 원문 이름은 `oracle price gate`입니다.

| 구분 | 기록된 조건 |
|---|---|
| 즉시 알림 (`urgent`) | 신호 가중합 2.0 이상 |
| 정기 요약 (`digest`) 후보 | `anomaly` 0.45 이상 또는 `why_now` 0.70 이상. 상위 N개를 요약 |
| 그 외 | 저장하고 미발송 사유 기록 |

점수의 세부 계산식과 N의 값은 공개 자료에 없습니다. 위 조건은 당시 개인용 설정입니다.

## 3. 피드백을 저장하고 구조화하기 — Feedback

자연어 답글이나 HTTP 요청을 받으면 먼저 원문을 저장합니다. 그다음 정규식 분류와 LLM 추출을 수행합니다.

```text
원문 저장 (queued)
    ├─ 초단문·이모지 수준 → 반영 (applied)
    └─ 그 외 → 정규식 1차 분류 → LLM 구조화 (llm_running)
                                  ├─ 추출 성공 → 검증 → 평가·신호·선호 반영
                                  └─ 추출 실패 (llm_failed)
                                       → 원문 유지 → recovery 작업 재시도
```

`applied`는 처리·반영 상태입니다. 저장 성공 후 추출이 실패하면 같은 원문으로 다시 시도합니다. 검증 실패 시의 세부 상태는 공개 자료에 없습니다.

### 선호 반영

이모지 평점과 자연어 피드백은 같은 선호 테이블에 합류합니다. 평점을 −1~+1로 정규화하고 카테고리·소스·가격대·브랜드 등의 feature key별 가중치를 지수이동평균(EMA, α=0.15)으로 갱신합니다. 자연어 신호는 confidence로 감쇠해 반영합니다.

[피드백 규모와 선호 갱신의 한계](OPERATIONS.md#preference)

### 부정적 평가의 이유 확인 — Rebuttal

싫은 이유가 이미 있으면 선호에 반영하고 추가로 묻지 않습니다. 이유가 없고 가격 근거가 강한 항목이면, 기준선 대비 저가라는 근거와 함께 이유를 한 번 더 요청합니다. 근거가 약하면 평가를 그대로 수용합니다.

추가 질문은 하루 1건으로 제한합니다. ‘비쌈·관심 없음·이미 있음·너무 잦음·품질 의심·직접 입력’ 응답을 `dislike_reason`에 남겨 선호 입력으로 사용합니다.

## 4. 지정한 상품 찾기 — Quest

`!찾아줘 <상품> [목표가]`로 요청을 등록하면 세 경로로 처리합니다.

| 경로 | 동작 |
|---|---|
| 능동 탐색 | 쇼핑 API와 내부 할인 이력을 20시간 간격으로 검색합니다. 제목 유사도·기준선 신뢰도·가격 상식선 검사를 통과한 결과를 보고합니다. |
| 신규 글 대조 | 이후 수집되는 글을 활성 요청과 비교하고, 일치하면 즉시 알립니다. |
| 목표가 감시 연결 | `deal_watch(target_price)`로 넘겨 계속 감시하는 경로가 있습니다. |

원문에서 감시 연결 조건은 ‘목표가 미달’로 표현돼 있으며, 상세 비교식은 제시돼 있지 않습니다.

`!목록`으로 활성 요청을 보고, `!그만 <상품>`으로 해제합니다.

## 5. 새 수집원 조사 — Source Scout

매일 LLM으로 후보 소스를 조사합니다. 바로 운영에 넣지 않고 120분 주기의 시험 수집(`shadow crawl`)에서 소스 점수를 확인합니다.

```text
후보 조사·등록 → 운영과 분리된 시험 수집 → 소스 점수 확인
                                        ├─ 미달 → 관찰 유지 또는 격리
                                        └─ 충족 → 편입 제안 → 사람 승인 → trusted
```

상태는 `discovery`(발굴), `warmup`(관찰), `quarantined`(격리), `trusted`(승인 후 운영 편입)로 기록합니다. 소스 점수의 세부 계산식은 미공개입니다.

## 6. 알림을 돌아보고 기준 변경 제안하기 — Self-review / Self-tuning

매일 23:30에 알림·미알림 항목을 돌아보고 `daily_reviews`에 기록합니다. `missed`는 좋은 할인으로 분류됐지만 보내지 않은 항목, `false-positive`는 보냈지만 반응이 좋지 않았던 항목입니다.

매주 일요일에는 `daily_reviews`와 `decision_log`의 14일치 기록을 바탕으로 변경안을 만듭니다.

```text
회고·결정 로그 → LLM 변경안 생성
                    └─ 생성 실패 시 규칙 기반 대안 사용
    ↓
허용된 파라미터 5개·값의 범위·1회 변경폭 검사
    ├─ 기각 → 사유 기록
    └─ 통과 → 변경안 저장·Discord 발송
                 ├─ !튜닝 승인 <id> → override 적용
                 ├─ !튜닝 거절 <id> → 기각
                 └─ 7일 무응답 → 만료
```

알림 임계값은 승인 뒤 적용하며 기본값으로 복원할 수 있습니다. 제안의 생성 경로도 함께 기록합니다. 파라미터의 역할과 효과 설명은 LLM이 새로 쓰는 대신 허용 목록의 사양에 둡니다. 제안 생성과 실제 변경 권한을 분리한 구조입니다.

첫 변경 제안과 승인 상태는 [운영 기록](OPERATIONS.md#tuning-record)에 정리했습니다.
