# 운영 사례와 수치

**2026-07-13 기준 개인용 운영 기록**입니다. 아래 수치는 당시 DB 측정과 구현 규모를 정리한 값이며, 현재 누적값이나 다중 사용자 서비스의 성과가 아닙니다.

## 기록된 규모

| 항목 | 기록된 값 |
|---|---|

| 코드 | Python 45개 모듈, 17,950줄 |
| 단위 테스트 | 33개 파일, 241개 함수, 5,593줄 |

수집·발송·로그 건수는 처리량, 소스 분포는 편입·격리 상태, 테스트 함수 수는 검사 규모입니다. 이 값만으로 추천 정확도나 누락 방지 효과를 알 수는 없습니다.

## 가격과 단위를 잘못 읽은 사례

**할인액을 판매가로 읽은 경우.** ‘5,000원 할인’을 상품의 판매가로 오인하는 문제가 있었습니다. 가격·할인액·조건부 혜택을 분리해 처리하고, 확인된 오인 사례에 회귀 테스트를 추가했습니다.

**저장 용량을 무게로 읽은 경우.** ‘512GB’의 G를 그램으로 읽어 노트북에 원/100g 단가가 계산된 사례가 있었습니다. 해당 표기를 제외하도록 정규식을 수정하고 회귀 테스트를 추가했습니다.

두 사례는 알려진 입력 오류에 대한 수정입니다. 모든 판매처의 가격·단위 해석이 정확하다는 결과는 아닙니다.

<a id="feedback-recovery"></a>
## LLM 추출에 실패한 피드백 재처리

원문을 먼저 저장한 피드백 중 LLM 추출이 실패한 8건을 다시 처리해 적용한 기록이 있습니다. 기록 시점의 처리 상태는 13건 중 13건이 `applied`였습니다.

이는 해당 피드백의 처리 완료이지 추출 정답률이나 일반적인 복구 성공률은 아닙니다. [원문 저장과 상태 전이](WORKFLOW.md#feedback)

<a id="preference"></a>
## 선호 갱신에 사용한 피드백의 한계

평점·자연어 피드백처럼 명시적인 라벨은 수십 건 수준이었습니다. 당시에는 선호 방향을 파악하는 정도로 보고, implicit 신호와 가격 기준선의 비중을 키웠습니다. 공개 자료에는 implicit 신호의 구체적 항목과 변경 전후 개인화 성능 비교가 없습니다.

결정 로그는 ‘왜 이 항목을 보내지 않았는가’를 확인하는 데 사용했습니다. 다만 수집되지 않은 할인 글까지 로그만으로 파악할 수 있다는 뜻은 아닙니다.

<a id="tuning-record"></a>
## 첫 알림 기준 변경 제안

첫 주간 실행에서는 14일치 기록의 ‘오탐 0건’, ‘근접 억제 103건’, ‘missed 112건’을 바탕으로 임계값 하향 2건이 제안됐습니다. **당시에는 승인 대기 상태**였습니다.

변경안 생성까지의 기록이며 적용 후 효과는 포함하지 않습니다. 분류별 정답 기준과 중복 여부가 제시돼 있지 않아 세 건수를 합산하거나 정확도·재현율로 환산할 수는 없습니다. [변경안 검사와 승인](WORKFLOW.md#tuning)
